# content

## voice

Use calm, direct, mostly lowercase language. Prefer short labels and short sentences. Name the object and action precisely. Do not use corporate filler, cute system copy during failure, or technical jargon when a plain word works.

## actions

Use verbs that predict the result: `save`, `retry`, `open in Obsidian`, `move 3 files`, `stop run`. Avoid vague labels such as `continue`, `confirm`, or `okay` when the result can be named.

## headings

Use the shortest unique destination or task name. Do not add marketing kickers, decorative subtitles, or repeated descriptions when the surrounding navigation already explains the page.

## helper text

Explain consequence or format, not the label again. Keep essential help visible. Put advanced explanation behind a deliberate details control only when the main task stays understandable.

## errors

State:

1. what failed;
2. the useful cause, if known;
3. what the owner can do next.

Example: `Could not save the note because it changed on disk. Reload it or save this draft as a copy.`

Never blame the owner or show a raw stack trace as the primary message.

## empty states

Say what belongs here and give at most one useful first action. Do not add illustration or filler copy just to occupy the screen.

## status

Prefer short, honest states: `saving`, `saved`, `offline`, `3 files selected`, `waiting for approval`, `partial results`. Use sentence case only when the status is a sentence.

## dates, time, and numbers

Respect the configured locale and time zone. Use tabular figures where values compare. Show units. Avoid ambiguous dates. Preserve full precision only where the task needs it.

## AI and providers

Show the actual provider and model when it matters. Do not label an unresolved choice as `automatic` after resolution. Separate model output, verified evidence, and system state clearly.
